## Findings (ranked; confirmed unless marked)

1. **FB-1, HIGH, OBSERVABLE-UNINTENDED, a regression against live `c5fc1fd1` (confirmed): Facebook Page posts can no longer be approved, and Facebook posts approved on the live build are held instead of published.**
   - *What breaks.* `Phase2Store.current()` (`src/postriff_phase2/store.py` lines 622-623 on RC1 and on the W-02 head `23af7a3a`) returns False for every Facebook manifest unless `manifest.destinationId == channel.destinationId`. No code in the candidate writes `manifest.destinationId` for Facebook (the only writer is Discord's `freeze_manifest`), so the check is false for every Facebook manifest, whether or not the channel has a Page id.
   - *For whom.* Every workspace with a Facebook Page connection. Whether Production has one is UNKNOWN from here (fastest check: the names-only Production env list for `POSTRIFF_OAUTH_FACEBOOK_*`, and with the owner's yes one read-only count of workspaces whose state holds a Facebook channel or a Facebook job that is not finished).
   - *On which paths.* (a) Preparing a Facebook review (`p2_review`): the review is born `stale`. (b) Approving it (`p2_approve`, also bulk approval and automation commits): refused with "Review and explicitly approve this exact destination manifest." (c) A Facebook post approved on the live build before promotion: `invalidate()`, which ends EVERY hosted command in that workspace and every worker claim of that workspace, moves it to `held` ("Approval, capability or entitlement changed. Review timing and approve a new job; reconnection does not release this one."), so it is not published at its time; the worker's own approval check would hold it as well ("Approval, account, media, timing or permission changed; a new review is required").
   - *Evidence.* `tests/test_customer_impact_shared_paths.py::test_a_facebook_page_post_is_approvable_as_on_live` (expectedFailure on RC1; the LinkedIn control `test_a_linkedin_post_is_approvable_as_on_live` passes): the same stored workspace state, run with the live tree, gives review `needs_review`, job `scheduled`, still `scheduled` after `invalidate()`; with the candidate tree, review `stale`, approval refused, the live-approved job `held`. Also true when the channel already carries a Page id.
   - *Why it is there (not intended).* Commit `381ac2d0` (2026-10-08, "preserve minimum Facebook connections") added three coordinated pieces: freeze the chosen Page id into the manifest and refuse a review without a chosen Page, check it in `current()`, record the Page id when the person chooses a Page. The Discord line's squash `17e3844c` carried only the last two. The live line has none of the three. Facebook is not in the release scope, and no RC test approves a Facebook post end to end.
   - *Smallest fix (verified in a scratch copy of RC1).* Delete the two-line Facebook clause in `Phase2Store.current()`; the state probe then gives exactly the live results. For exact parity also remove the Facebook branch that RC1 added to `OAuthService.choose_destination` (`oauth.py` lines 1079-1094: it relabels the channel to the Page, rewrites its capability rows and runs `invalidate()` when a Page is chosen, row UI-9 below). Then remove the `expectedFailure` decorator from the test. Shipping the full `381ac2d0` Page binding instead is a separate change: it would refuse every review on the Page-less Facebook channels the live build created until the person chooses a Page again.
2. **CH-1, MEDIUM, side effect on every Channels read (confirmed and measured):** `OAuthService.channels()` now calls `discord_connections.public_identities()` whenever `POSTRIFF_DISCORD_CONNECTIONS_V2_ENABLED=true` (set in Production) and the Discord adapter is mounted. That opens a second repository transaction: one more Supabase Auth `getUser` HTTPS call, one more database connection for session flags, one more connection for the transaction and an extra `FOR UPDATE OF w` lock on the workspace row, to return `[]` for every workspace that never linked Discord. Measured on real PostgreSQL: one more database connection and one more `SELECT ... FOR UPDATE OF w` per Channels read (`test_pins_the_size_of_the_extra_channels_read_transaction`; the synthetic verifier hides the Supabase call and the session-flag connection, which Production adds per call: inference from `supabase_verifier`). The channels endpoint backs Channels, Overview, Home, Growth, Account and other pages. Fix: read `discordIdentityLinks` from the snapshot `channels()` already loaded, or skip the call when the state has no links.
3. **WB-1, MEDIUM, OBSERVABLE-INTENDED but not "Discord only": the worker budget changes for every provider.** The live code already reads `POSTRIFF_WORKER_MAX_JOBS` and `POSTRIFF_WORKER_MAX_SECONDS` (defaults 10 jobs, 20 s). The two values set on 2026-10-23 (25, 40) apply to every new build, including any rebuild of the live line, so the minute worker for all providers will run up to 25 jobs and 40 s per minute instead of 10 and 20. Approved as packet row 3 ("project-wide, all providers"); the statement that the seven variables "only matter to builds that contain the code" is not true for these two.
4. **SC-1, LOW to MEDIUM, scope: non-Discord changes ride in the candidate.** Besides FB-1, the Discord line carries changes every customer can see or that change behaviour outside Discord (details in the tables): a "Save as draft" button and help text on Home for every editor (`manual_draft_create`), review preparation (`p2_review`) no longer requiring a live publishing entitlement, composer input handling on native and autofill input, the billing Storage line, the workspace switcher's accessible name, the history-import button text, Facebook and Google Business Profile destination-picker wording and toasts, Pillow 12.3.0 to 13.0.0 (major) and pypdf 6.19.0 to 6.21.1, a new `psycopg-pool` dependency. `RC-RECEIPT.md` describes the non-Discord delta as only the Next.js/Sentry patch and pypdf "6.20.1 to 6.21.1"; live pins pypdf 6.19.0 and Pillow 12.3.0.
5. **BG-1, LOW to MEDIUM, new background load each minute (confirmed and measured):** with `POSTRIFF_DISCORD_WORKER_V1_ENABLED=true` (set in Production) every minute tick now also runs a Discord lane claim attempt (a new database connection and 4 statements per attempt, about every other loop iteration while the generic queue is busy), `discord_report()` (one connection; reads up to 256 workspace state documents, the first 256 by id, every minute) and, with `POSTRIFF_DISCORD_RATE_LIMITS_V1_ENABLED=true`, the rate limiter report (one connection, 2 bounded statements). No customer-visible effect; cost is database time and connections. Measured on real PostgreSQL with Production's variables: an idle tick goes from 1 connection and 3 statements (live) to 4 and 11; a tick with one ordinary post due goes from 4 and 21 to 8 and 33, with the same outcome and the same writes (`test_pins_the_minute_workers_extra_reads_with_no_discord_work`). Per idle day that is about 4,300 more connections and 11,500 more statements, and up to 256 workspace state documents read 1,440 times.
6. **PR-1, LOW, new public route with 5xx noise:** `POST /api/discord/interactions` is answered before the bearer and origin checks. With the user-install flag unset it returns 503 (`discord_interaction_unavailable`), which the request logger writes at ERROR level; live answered the same request through the normal authenticated path (4xx). Any scanner can create ERROR lines and 5xx counts.
