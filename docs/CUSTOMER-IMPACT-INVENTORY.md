## Findings (ranked; confirmed unless marked)

1. **FB-1, HIGH, OBSERVABLE-UNINTENDED (confirmed by probe): Facebook publishing breaks in the candidate.** `Phase2Store.current()` in RC1 refuses every Facebook manifest unless `manifest.destinationId == channel.destinationId`, but no code in RC1 ever writes `manifest.destinationId` for Facebook. The check came from commit `381ac2d0` (2026-10-08), which had three coordinated pieces (freeze the Page id into the manifest, check it in `current()`, write it at Page choice); the integration commit `17e3844c` carried only the last two. Effect for any workspace with a Facebook Page connection: a new Facebook review is born `stale` and cannot be approved ("Review and explicitly approve this exact destination manifest."), and a Facebook post already approved on the live build is **held** at the next `invalidate()`, which runs at the end of every workspace command and at every worker claim of that workspace ("Approval, capability or entitlement changed. Review timing and approve a new job; reconnection does not release this one."). Live: review `needs_review`, `current` true, approval succeeds. Evidence: `tests/test_customer_impact_shared_paths.py::FacebookApprovalUnchanged` (pending). Whether any Production workspace has a Facebook connection or queued Facebook post is UNKNOWN from here. Fix: remove the two Facebook hunks (`store.py` `current()`, `oauth.py` `choose_destination`) so Facebook behaves exactly as live, or ship all three pieces of `381ac2d0` deliberately with its own tests and a migration plan for Page-less channels.
2. **CH-1, MEDIUM, side effect on every Channels read (confirmed by code reading, measured by test, pending):** `OAuthService.channels()` now calls `discord_connections.public_identities()` whenever `POSTRIFF_DISCORD_CONNECTIONS_V2_ENABLED=true` (set in Production) and the Discord adapter is mounted. That opens a second repository transaction: one more Supabase Auth `getUser` HTTPS call, one more database connection for session flags, one more connection for the transaction and an extra `FOR UPDATE OF w` lock on the workspace row, to return `[]` for every workspace that never linked Discord. The channels endpoint backs Channels, Overview, Home, Growth, Account and other pages. Fix: read `discordIdentityLinks` from the snapshot `channels()` already loaded, or skip the call when the state has no links.
3. **WB-1, MEDIUM, OBSERVABLE-INTENDED but not "Discord only": the worker budget changes for every provider.** The live code already reads `POSTRIFF_WORKER_MAX_JOBS` and `POSTRIFF_WORKER_MAX_SECONDS` (defaults 10 jobs, 20 s). The two values set on 2026-10-23 (25, 40) apply to every new build, including any rebuild of the live line, so the minute worker for all providers will run up to 25 jobs and 40 s per minute instead of 10 and 20. Approved as packet row 3 ("project-wide, all providers"); the statement that the seven variables "only matter to builds that contain the code" is not true for these two.
4. **SC-1, LOW to MEDIUM, scope: non-Discord changes ride in the candidate.** Besides FB-1, the Discord line carries changes every customer can see or that change behaviour outside Discord (details in the tables): a "Save as draft" button and help text on Home for every editor (`manual_draft_create`), review preparation (`p2_review`) no longer requiring a live publishing entitlement, composer input handling on native and autofill input, the billing Storage line, the workspace switcher's accessible name, the history-import button text, Facebook and Google Business Profile destination-picker wording and toasts, Pillow 12.3.0 to 13.0.0 (major) and pypdf 6.19.0 to 6.21.1, a new `psycopg-pool` dependency. `RC-RECEIPT.md` describes the non-Discord delta as only the Next.js/Sentry patch and pypdf "6.20.1 to 6.21.1"; live pins pypdf 6.19.0 and Pillow 12.3.0.
5. **BG-1, LOW to MEDIUM, new background load each minute (confirmed by code reading, measured by test, pending):** with `POSTRIFF_DISCORD_WORKER_V1_ENABLED=true` (set in Production) every minute tick now also runs a Discord lane claim attempt (a new database connection and 4 statements per attempt, about every other loop iteration while the generic queue is busy), `discord_report()` (one connection; reads up to 256 workspace state documents, the first 256 by id, every minute) and, with `POSTRIFF_DISCORD_RATE_LIMITS_V1_ENABLED=true`, the rate limiter report (one connection, 2 bounded statements). No customer-visible effect; cost is database time and connections.
6. **PR-1, LOW, new public route with 5xx noise:** `POST /api/discord/interactions` is answered before the bearer and origin checks. With the user-install flag unset it returns 503 (`discord_interaction_unavailable`), which the request logger writes at ERROR level; live answered the same request through the normal authenticated path (4xx). Any scanner can create ERROR lines and 5xx counts.
