## 1. Findings, ranked (each with the smallest fix or test)

1. **FB-1, HIGH, OBSERVABLE-UNINTENDED, a regression against live `c5fc1fd1` (confirmed): Facebook Page posts can no longer be approved, and Facebook posts approved on the live build are held instead of published.**
   - *What breaks.* `Phase2Store.current()` (`src/postriff_phase2/store.py` lines 622-623 on RC1 and on the W-02 head `23af7a3a`) returns False for every Facebook manifest unless `manifest.destinationId == channel.destinationId`. No code in the candidate writes `manifest.destinationId` for Facebook (the only writer is Discord's `freeze_manifest`), so the check is false for every Facebook manifest, whether or not the channel has a Page id.
   - *For whom.* Every workspace with a Facebook Page connection. Whether Production has one is UNKNOWN from here (fastest check: the names-only Production env list for `POSTRIFF_OAUTH_FACEBOOK_*`, and with the owner's yes one read-only count of workspaces whose state holds a Facebook channel or a Facebook job that is not finished).
   - *On which paths.* (a) Preparing a Facebook review (`p2_review`): the review is born `stale`. (b) Approving it (`p2_approve`, also bulk approval and automation commits): refused with "Review and explicitly approve this exact destination manifest." (c) A Facebook post approved on the live build before promotion: `invalidate()`, which ends EVERY hosted command in that workspace and every worker claim of that workspace, moves it to `held` ("Approval, capability or entitlement changed. Review timing and approve a new job; reconnection does not release this one."), so it is not published at its time; the worker's own approval check would hold it as well ("Approval, account, media, timing or permission changed; a new review is required").
   - *Evidence.* `tests/test_customer_impact_shared_paths.py::test_a_facebook_page_post_is_approvable_as_on_live` (expectedFailure on RC1 and RC2; the LinkedIn control `test_a_linkedin_post_is_approvable_as_on_live` passes): the same stored workspace state, run with the live tree, gives review `needs_review`, job `scheduled`, still `scheduled` after `invalidate()`; with the candidate tree, review `stale`, approval refused, the live-approved job `held`. Also true when the channel already carries a Page id.
   - *Why it is there (not intended).* Commit `381ac2d0` (2026-10-08, "preserve minimum Facebook connections") added three coordinated pieces: freeze the chosen Page id into the manifest and refuse a review without a chosen Page, check it in `current()`, record the Page id when the person chooses a Page. The Discord line's squash `17e3844c` carried only the last two. The live line has none of the three. Facebook is not in the release scope, and no RC test approves a Facebook post end to end.
   - *Smallest fix (verified in a scratch copy of RC1).* Delete the two-line Facebook clause in `Phase2Store.current()`; the state probe then gives exactly the live results. For exact parity also remove the Facebook branch that RC1 added to `OAuthService.choose_destination` (`oauth.py` lines 1079-1094: it relabels the channel to the Page, rewrites its capability rows and runs `invalidate()` when a Page is chosen, row API-10). Then remove the `expectedFailure` decorator from the test. Shipping the full `381ac2d0` Page binding instead is a separate change: it would refuse every review on the Page-less Facebook channels the live build created until the person chooses a Page again.
2. **CH-1, MEDIUM, OBSERVABLE-UNINTENDED side effect on every Channels read (confirmed, measured).** `OAuthService.channels()` now calls `discord_connections.public_identities()` whenever `POSTRIFF_DISCORD_CONNECTIONS_V2_ENABLED=true` (set in Production) and the Discord adapter is mounted. That opens a second repository transaction: one more Supabase Auth `getUser` HTTPS call (12 s timeout), one more connection for the session-flag query, one more connection for the transaction and a `SELECT ... FOR UPDATE OF w` lock on the workspace row, to return `[]` for every workspace that never linked Discord. *Measured:* +1 connection and +1 locking read per Channels read (`test_pins_the_size_of_the_extra_channels_read_transaction`); the synthetic verifier hides the Auth call and the session-flag connection, which Production adds per call (inference from `supabase_verifier`, which has no cache). The endpoint backs Channels, Overview, Home, Growth, Account and other pages, so it is paid on most page loads; latency rises by one Auth round trip (size UNKNOWN; fastest check: `durationMs` of `request.completed` for `GET .../channels` on D1 versus live). *Fix:* build the list from the snapshot `channels()` already read (`snapshot['state']['phase2']['discordIdentityLinks']`), or skip the call when that list is absent; then remove the decorator of `test_channels_read_opens_no_more_database_transactions_than_live`.
3. **UI-1, MEDIUM-LOW, OBSERVABLE-UNINTENDED: every customer sees a new "Personal Discord accounts" section on Channels while Discord is closed to them.** `channels-view.tsx` renders `DiscordPersonalAccounts` whenever the Discord provider reports `discordConnectionsV2` (true in Production), regardless of the gate. A member with manage permission sees the heading "Personal Discord accounts", a disabled button "Connect personal Discord account", "Connecting your account does not authorize publishing as you. …", "New connections are currently unavailable. Existing account records remain visible." and "No personal Discord account linked."; other members see "Managing these connections requires the appropriate workspace permission." *Evidence:* the candidate's channels answer carries `discordConnectionsV2: true` for every ordinary workspace (`test_channels_listing_keeps_discord_closed_for_ordinary_workspaces`); component code. *Fix:* render the section only when `provider.discordAccess?.status === 'open'` or `discordIdentities.length > 0`.
4. **SC-1, MEDIUM-LOW, OBSERVABLE-UNINTENDED: non-Discord changes ride in the candidate.** The release is described as "live line + Discord v2 + framework patch + gate and cap", but the Discord line brought changes from other lines that every customer meets: the scheduling dialog's Draft and Account pickers became native selects without platform icons and gained a UTC time line (UI-10, from `06f4f13c`); a "Save as draft" button and help text on Home for every editor (UI-12, new action `manual_draft_create`); review preparation no longer checks the publishing entitlement (API-8, `ea59babb`; *measured*: one entitlement read set fewer per review); composer input handling (UI-13); the billing Storage line (UI-14); the workspace switcher's accessible name (UI-15); the history-import button text (UI-16); connect-sheet tiles locked while a connection is starting (UI-3); Facebook and Google Business Profile destination-picker wording (UI-8). `RC-RECEIPT.md` names only the Next.js/Sentry patch and "pypdf 6.20.1 to 6.21.1" as non-Discord; live actually pins pypdf 6.19.0 and Pillow 12.3.0 (DEP-5, DEP-6). *Fix:* the owner accepts this list explicitly as part of the release, or the parts not wanted are reverted to live with their tests.
5. **WB-1, MEDIUM, OBSERVABLE-INTENDED (packet row 3) but not "Discord only": the minute worker's budget rises for every provider.** The live code already reads `POSTRIFF_WORKER_MAX_JOBS` and `POSTRIFF_WORKER_MAX_SECONDS` (defaults 10 jobs, 20 s). The values set on 2026-10-23 (25, 40) reach every new build, including any rebuild of the live line: up to 2.5 times as many scheduled posts per minute for all providers and up to twice the worker time per minute (function duration cost). *Measured:* both trees report `budget {maxJobs: 25, maxSeconds: 40}` (`test_worker_budget_comes_from_the_environment_on_both_builds`). The statement that the seven variables "only matter to builds that contain the code" is not true for these two. Rolling back by promoting `dpl_47SG` keeps 10/20; rebuilding live would not.
6. **BG-1, LOW-MEDIUM, OBSERVABLE-UNINTENDED side effect: more background database work every minute (measured).** With `POSTRIFF_DISCORD_WORKER_V1_ENABLED=true` each minute tick adds Discord lane claim attempts (1 connection, 4 reads each; one when idle, about every other loop iteration while other providers' posts are due), `discord_report()` (1 connection; reads up to 256 workspace state documents, the first 256 by id, every minute) and, with `POSTRIFF_DISCORD_RATE_LIMITS_V1_ENABLED=true`, the rate report (1 connection, 3 reads). Idle tick: live 1 connection / 3 statements, candidate 4 / 11. One ordinary post due: live 4 / 21, candidate 8 / 33, same outcome, same writes (`test_pins_the_minute_workers_extra_reads_with_no_discord_work`, `test_minute_worker_treats_an_ordinary_post_exactly_as_live`). About 4,300 more connections and 11,500 more statements a day when idle, plus 1,440 reads of up to 256 state documents. *Fix if unwanted:* run `discord_report()` and the Discord lane attempt only when the projection holds a due Discord hint (`SELECT 1 FROM pr_discord_worker_projection WHERE next_at IS NOT NULL LIMIT 1`).
7. **RC2-1, LOW, OBSERVABLE-UNINTENDED side effect (RC2 only): twelve new per-minute crons.** `vercel.json` adds `/api/cron/discord-worker/0..11` every minute: 17,280 more function invocations and 17,280 more `request.completed` log lines a day, with the lane flag off. *Measured:* off, a shard answers from the environment alone: 0 connections, 0 statements (`test_w02_shard_does_nothing_with_the_lane_flag_off`, `test_w02_shard_answers_without_the_runtime_when_the_lane_flag_is_off`). If the lane flag is turned on, each idle invocation opens 4 connections for 7 reads (about 69,000 connections a day before any Discord post) and logs `discord.lane.completed` (`test_pins_w02_shard_cost_with_the_lane_flag_on_and_no_discord_work`). Cost of the invocations themselves: UNKNOWN (fastest check: the Vercel usage page for function invocations a day after promotion).
8. **PR-1, LOW, OBSERVABLE-UNINTENDED: a new public route that answers 503.** `POST /api/discord/interactions` is handled before the bearer and origin checks (like the Telegram and billing webhooks). With the user-install flag unset a JSON POST answers 503 `discord_interaction_unavailable` (or 400 before that if Vercel's Python runtime reports the request scheme as `http`; which one is UNKNOWN: one POST to the staged D1 settles it; other bodies get 415 or 413); the request logger writes every 5xx at ERROR level and the founder request metrics count it as 5xx. Live sends the same request down the normal authenticated path (inference: a 401 or 403 from the session or origin check, logged at INFO). Anyone can create ERROR lines and 5xx counts. *Fix:* answer 404 while the feature is off. A GET now answers 404 instead of falling into authentication (`test_the_new_interactions_route_answers_get_before_authentication`).
9. **DEP-1, UNKNOWN: the framework patch could change pages for everyone.** next 16.3.8 to 16.4.2 (a minor release), @sentry/nextjs 10.74.0 to 10.76.2 and 42 other lockfile moves. The web app could not be built here (no `node_modules`, Node 22 instead of 24, no network). *Fastest verification:* fetch the routes in `docs/impact-routes.txt` from `dpl_47SG` and from the staged candidate and run `scripts/impact_compare.py compare` (section 10, item 1), and compare the route table of the two `next build` logs.
10. **ENV-1, LOW: a malformed pool setting would take the whole API down.** `runtime_from_environment` now runs `int()` on `POSTRIFF_DB_POOL_MAX_CONNECTIONS` and `POSTRIFF_DB_POOL_MAX_WAITING` even when the pool is off; a non-integer value fails runtime construction, so every runtime route answers 503. Unset today (inference; verify in the names-only list).
