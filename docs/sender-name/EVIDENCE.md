## 8. Exceptions, risks and what is NOT verified

1. **Bot nickname is OFF by default and has never run against real Discord.** `CHANGE_NICKNAME`, the role hierarchy, the audit-log reason header and the verification read are modelled, not observed. Live acceptance in a disposable server is required before the capability is switched on.
2. **Webhook names have never run against real Discord and the webhook route is dark in Wave 1** (`POSTRIFF_DISCORD_WEBHOOK_V1_ENABLED`/`_QUALIFIED` unset): Discord's own handling of `username`, and the author name in the read-back, are modelled.
3. **Migration 131** (admission credential kind `webhook`) is required in Production for any webhook execute; it is not part of this branch. The shared W-02 lane fixture does not apply it (`CAPACITY-NOTES.md`).
4. **Symmetric authority:** while two Rafii workspaces hold installations of one server, neither can change its nickname. Chosen over a first-come lease to avoid a Production migration. A stale but unrevoked installation keeps the lock closed (fails closed).
5. **The rate coordinator is not changed by this branch.** Until the owner of `rate_limits.py` takes R1 to R4 (`REQUESTS-TO-RATE-LIMITER.md`): the nickname route is allowlisted unconditionally; a lost write after a bot-token rotation, or after a workspace deletion, leaves one `uncertain` admission that counts as pending without an age bound (the reviewer measured the application window 25 to 24); and a 403 on the nickname PATCH embargoes that server's route for the policy lifetime (measured here on PostgreSQL 16: next attempt `discord_rate_delayed`, 86340 s).
6. A bot nickname cannot be cleared from Rafii (`discord_sender_reset_unsupported`); a webhook name can.
7. The reserved-word and confusables logic is a compact heuristic, not the Unicode confusables table. Discord applies further private rules to names that were not observable.
8. **Mutation survivors:** 37 of 443 deletion mutants survive every suite; each is classified in section 4 (equivalent, unreachable or redundant with a neighbouring check). That is a statement about these tests, not a proof of correctness.
9. **PostgreSQL:** local runs used PostgreSQL 16; CI uses 17; the owned cloud qualification was not run.
10. **Secret scan:** `scripts/consumer_ready_secrets.py` at the code head prints `status FAIL`, 9 unexpected findings, all in six files that are byte-identical to `5a94b4f2` and belong to other lanes: `tests/discord_ops_drills.py:58`, `tests/impact_scenario.py:157`, `tests/rc2_shared_path_scenario.py:139`, `tests/test_customer_impact_dependencies.py:123`, `tests/test_impact_compare.py:250,253,257`, `tests/test_rc2_shared_path_fixes.py:356,359`. The scanner configuration finds the same 9 in the pristine `5a94b4f2` export. None is in a file this branch adds or changes (the per-file scan with the repository's configuration passes at every commit). No allowlist or scanner exception was added, and the other lanes' files were not edited; the remedy is to build those literals at run time. The scan on the final head is reported in the handback (only documents and in-memory tests were added after `df990afb`).
11. **Baseline `5a94b4f2`:** the same discovery on the pristine export failed 3 of 675 tests: `test_discord_parallel_lane_postgres` `test_many_loops_create_every_post_exactly_once` and `test_one_busy_workspace_cannot_starve_the_others` (jobs ended `held`) and `test_discord_ops_drills_postgres` `test_d3_rate_limit` (error), all PostgreSQL W-02 or drill tests, while the machine ran at load 25 to 30. At the head the whole discovery passes at load 2 to 4. The cause at the base was not investigated; this branch changes none of those tests or the code they exercise beyond what the discovery covers.
12. **Not run:** the 5,000-post load, the browser acceptance of the settings page, any hosted or Production check, the independent reviewer's own proof-of-concept scripts (their 27 tests were adapted and run; section 5, SNR-3).
13. **The sensitive-action gate does not protect the POST** (`security_gate.require` is a no-op unless `RAFII_ACCOUNT_PROTECTION_V2_MODE=enforce`, set nowhere). The effective controls are the fresh sign-in, the application guard header, the role check and the exact-state fingerprint; the upstream documents claimed the gate.
14. **Rollback:** RC1 holds approved manifests that carry a frozen webhook name and silently drops the name on new approvals (SNR-9).
