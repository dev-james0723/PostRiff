# BUILD VIA GITHUB ACTIONS (route A): D1 and D2 when no machine has the Vercel CLI

The owner's laptop cannot be turned on, so the two approved builds (D1 dark, D2 open; `AUTHORIZATION-RECORD.md`, rows 5 and 6) are made by a GitHub Actions workflow instead of the commands in `BUILD-RUNSHEET.md`. Nothing about the rows changes: same frozen SHA, same two builds, same `--prod --skip-domain`, same cap line, same read-backs and acceptance. Only the machine that runs `vercel deploy` is different. **This repository is public: every log line, step summary and file here is world-readable.**

Files: `deploy/rc-staged-build.yml` (the workflow; inert here, it only runs from a request branch), `deploy/run_tests.py` (offline tests), `deploy/make_request_branch.sh`, `deploy/cli/` (the reviewed CLI lock file), `deploy/vercel-deploy-help.txt` (the real `vercel deploy --help` of the pinned CLI).

## 1. What the owner set up (once)

GitHub, repository settings, Environments, `rafii-rc-deploy`. In this order:

1. Required reviewers: the owner. **Prevent self-review: off** (the owner's account is also the pusher; with it on, nobody can approve).
2. Deployment branches and tags: selected, pattern `claude/discord-launch-rc-deploy-*`.
3. Environment **secret** `VERCEL_TOKEN`: a Vercel token scoped to the one team, expiring in one day, added only after steps 1 and 2. Never a repository-level secret (those are visible to every workflow).
4. Environment **secret** `TESTER_WORKSPACE_ID` (the dark twin's connect gate: the tester workspace id for the first route; from version 4b one to three workspace ids separated by single commas, see section 8; used by the D1 build only). A secret and not a variable, because a variable is printed in clear in the step header of a public log. The ids themselves are deliberately **not** in this repository.

What is proven by the first run, not assumed: a pushed request branch shows a run in the state `waiting` (the required-reviewer gate), and nothing runs until the owner approves it.

## 2. A request branch

`claude/discord-launch-rc-deploy-{preflight,d1,d2}-<suffix>`: an orphan commit made by `make_request_branch.sh` that holds exactly five files: `.github/workflows/rc-staged-build.yml`, `deploy/REQUEST.json` (`{"sha": <40 hex>, "cap": "<n>"}`; no cap for preflight), `deploy/cli/package.json` and `package-lock.json`, and a root `vercel.json` with `git.deploymentEnabled=false` (belt and braces: a push of this branch must never start a hosted Git deployment). No other workflow exists on that branch and no existing workflow triggers on those branch names.

## 3. What a run does, in order (and what it refuses)

| Step | Behaviour |
|---|---|
| Job `if` | only in `dev-james0723/PostRiff`, only for the actor `dev-james0723`; then waits for the environment's reviewer |
| Read the request | refuses re-runs (`run_attempt` must be 1) and a request commit older than twelve hours; reads `sha` and `cap` and accepts them only as whole-string matches (40 lower-case hex; 1 to 999999); the SHA must be the current tip of `claude/discord-launch-rc-20261023`; CI on that SHA is read once: 14 check runs, none unfinished or red, the 11 named jobs must be `success` (a skipped job cannot stand in), the list must equal its total and not be cut at 100; names missing are printed |
| Install the CLI | `npm ci --ignore-scripts` from the reviewed lock file (390 packages, integrity on every entry, registry only); the exact tree that was reviewed, no install scripts |
| Fetch the frozen SHA | manual exact-SHA fetch (the repository has two orphan vendor gitlinks that the generic checkout cannot survive; the repo's own workflows do the same) |
| `preflight` | read-only; every check is reported and the step fails at the end if any failed: token shape, CLI version, deploy flags exist, token accepted for the team scope (never prints whose), production env **names** only (never values), the six required names present, names that must not exist yet, tester secret set and UUID-shaped (from version 4b only the count and a 12-character fingerprint of the sorted list are printed), tree and `vercel.json` checks, and `vercel deploy --dry --json` with the build's flags (reads the project and the files, uploads nothing, creates nothing), with a guard on the upload set |
| `d1` / `d2` | validates again, then exactly one `vercel deploy --prod --skip-domain --yes --scope <team> --meta rafiiSourceSha=<sha> --meta rafiiTwin=dark\|open --env POSTRIFF_DISCORD_CONNECT_WORKSPACES=<gate list>\|* --env POSTRIFF_OAUTH_DISCORD_REVIEWED=true --env POSTRIFF_DISCORD_GUILD_CAP=<cap>`; no retry; prints the deployment URL and id only (and, for `d1`, how many ids the gate holds and their fingerprint, also in the step summary); fails if the CLI wrote into the tree or if the inspect text shows a customer-facing alias (`rafii.io` or a subdomain, or the project's public `postriff-phase2-private.vercel.app`); the project's internal team-scoped default domain, which Vercel moves to every production build, is only noted |

Never done by the workflow: promote, alias, change an env variable or a project setting, merge, or touch the live deployment.

## 6. What cannot be proven offline (so it is watched on the first runs)

Header masking of the secret in a real Actions log; job-level `concurrency` order against the environment approval (a push by anyone else should show a skipped run and leave the owner's waiting run alone); the live check-run names (they matched the 14 seen on PR #222 when the list was written); whether the server accepts the `services` project settings without `skipAutoDetectionConfirmation` (the build keeps `--yes` for that reason); `--skip-domain` also covering the `*.vercel.app` production alias (the inspect text is checked in the job and the agent reads the aliases through the API afterwards); Deployment Protection still being `all_except_custom_domains` (read through the API).

Known and accepted: the pinned CLI tree includes `tar@7.5.7`, which npm reports as deprecated with published vulnerabilities in extraction. The deploy path packs and does not extract untrusted archives. Not fixable here without leaving the reviewed tree.

## 7. How each run goes

1. The agent checks the RC tip and CI, builds the request branch, pushes it, and reads the run state until it is `waiting`.
2. The agent gives the owner the run link, the request commit (short SHA) and the title. The owner compares them and approves in GitHub.
3. The agent reads the job log (public, so it is short by design), then checks the result through the Vercel API (project, SHA, target, state, aliases, files), not through the workflow.
4. D1 and D2 are the only builds (`AUTHORIZATION-RECORD.md`, row 6). A failed build is reported; a third build needs a new yes. The token is revoked by the owner after D2, and the request branches are deleted.

## 8. Version 4b (independently reviewed twice; nothing has been built from it yet)

Since owner reply 12 (`RELEASE-DEFINITION-v2.md`) the release is the open build, and the dark twin is only a verification step. Two consequences for this route:

- **The "D1 and D2 only" limit in section 7 applies to the frozen head `2a5a523d` and to nothing else.** A new frozen SHA (RC2, W-02 integrated) gets its own builds, each approved by its own packet; the existing approvals do not carry over.
- **The dark twin's connect gate must admit more than one workspace.** The tester session (G3) and the hosted A/B isolation probe (G4) need the tester workspace and the two throwaway accounts A and B, each with real Discord objects. Version 4b therefore lets the environment secret `TESTER_WORKSPACE_ID` hold **one to three lower-case workspace UUIDs separated by single commas** (the tester workspace, A and B; a space, an empty item, an upper-case letter, a fourth id, `*`, a non-ASCII look-alike character or a line break is refused). `launch_gate.py` already accepts a comma-separated list. The open build (`d2`) is unchanged: gate `*`, the cap, the reviewed flag.
- **The log shows how many ids went into the build, and a fingerprint of them, never the ids.** Both the preflight and the `d1` build print `N workspace id(s), fingerprint <12 hex>` (the build also writes it to the step summary). The owner recomputes the fingerprint from the ids she or he knows with `printf '%s\n' <id> <id> <id> | LC_ALL=C sort | sha256sum | cut -c1-12`; a different count or fingerprint means the secret is not what was intended, and the build must not be approved. The ids are random version-4 UUIDs (at least 122 random bits each), so the 48-bit fingerprint cannot be used to recover an id; anyone who already holds a candidate list can confirm it, and two builds made from the same list can be linked. On a Mac, where `sha256sum` may be missing, use `shasum -a 256` instead; the result is the same. Run a preflight immediately before the `d1` request and do not edit the secret in between (it is read again at every run).
- **Version 4b after the independent delta review of version 4** (reviewer's report, 2026-10-23: *ready for use after the owner sets the secret; no CRITICAL or HIGH finding*; 64 hostile inputs against the shape check, 25 mutants, the pinned CLI's own argument parser run offline). Applied: the count and fingerprint above (MEDIUM-1); `LC_ALL: C` for every step, because in many locales a range such as `[0-9a-f]` also matches accented letters and other-script digits (LOW-1; none of those could have admitted a workspace, but the claim "upper case is refused" was only true in C-like locales); the masks are emitted from a here-string, which `set -x` never prints, so a debug edit that turns tracing on cannot leak an id before its mask exists (LOW-2); the bound is three ids, the stated need, not five (LOW-4); wording that still assumed one id (LOW-5). Tests (LOW-3): every `d1` line that contains an id must be a mask line, the masks must come first, a traced (`bash -x`) build is run through a model of the runner's masker and must show no id, the model is shown to catch the old pattern, and the three mutants the reviewer found alive (masks after the deploy, ids echoed before masking, `set -x`) are now caught, together with five more of mine (no `LC_ALL`, the old five-id bound in either regular expression, no count line, no summary line).
- Changes against version 3: `rc-staged-build.yml` (two regular expressions, the masking, the count and fingerprint, `LC_ALL`), `run_tests.py` (196 offline checks). Fingerprint (sha256, first 16 characters): version 4b `ad069ffec374cabf`; the lock file is unchanged (`7dc4bca4d2ed2af5`). `action-validator` and `shellcheck` report nothing.
- **First hosted check after a dark build made from a list:** every listed workspace's connect catalog must read `discordAccess.reason = allowlisted`, and a fresh unlisted workspace must read `invite_only`. `misconfigured` means the value arrived mangled (this route cannot read the value back from the deployment: `vercel inspect` shows no variable values).
- Not verifiable offline: how the Vercel API stores and injects a comma-separated `--env` value (the first build used a single id), the hosted runner's real stdout/stderr interleaving, and which encodings the runner applies to `::add-mask::` values.
- **Status:** the delta from version 4 was re-reviewed independently (2026-10-23, commit `a5ac1a66`): *ready for use after the owner sets the secret*; no CRITICAL, HIGH or MEDIUM finding. Its two LOW findings (the fingerprint tests did not pin the sort or the duplicate rule; the locale was pinned only by the shape check) are closed in the test suite (201 offline checks), and the wording leftovers are fixed. The owner's `TESTER_WORKSPACE_ID` secret must be set to the list before a request branch is built (the agent cannot read or set it).
