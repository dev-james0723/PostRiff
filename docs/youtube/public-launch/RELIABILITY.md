## Durable upload and publication behavior

The upload journal binds workspace, connection, idempotency key, immutable manifest digest, private-storage object identity, and encrypted resumable session. Intent commits before remote initiation. Each lease probes Google's accepted range before sending another bounded chunk. A timeout, unknown initialization outcome, expired session, or missing journal never opens an automatic replacement upload. Processing, private upload, accepted native schedule, and verified publication remain distinct states.

The upload always starts private. A separately verified finalization applies exact approved visibility or a native `status.publishAt` schedule. The future-time guard remains in place at finalization. API dispatch additionally requires at least 60 seconds of remaining scheduling lead, both before and immediately after quota admission. A timestamp that expires or enters that buffer while waiting is held before provider transport and requires a new exact schedule review. Null/omitted timestamps used by explicit schedule cancellation are not converted into publication. Dedicated schedule/cancel actions re-read the owned video and verify provider state. An already published video cannot be recalled by canceling a workflow.

Private-now/native-future scheduling and a queued later upload remain different: the shared job timing controls when upload execution starts; `publishOptions.publishAt` controls YouTube's future public release after private processing. Owners must leave enough time for upload/processing. Approval expiry, quota delay, or missed native publication time requires review; no fallback silently changes it to immediate publication.

`POSTRIFF_YOUTUBE_UPLOAD_CHUNK_BYTES` defaults to **8 MiB**, must be a multiple of 256 KiB, and cannot exceed 8 MiB (the private-storage range ceiling). Each lease sends at most one chunk. This bounds media memory and avoids reading a complete large video into a function. The Library/backend bucket limits and channel eligibility still govern accepted video size; a chunk setting does not increase storage or Google capacity.

## Quota admission and tenant scheduling

Migration `097_youtube_capacity.sql` adds server-only, RLS-protected daily counters, per-workspace request windows, and durable worker dispatch cursors. If it is absent, workers defer YouTube jobs for 60 seconds with `capacityIntervention.code: youtube_capacity_schema`, preserving the original operation, approval, journal and attempt count; other platforms continue through the bounded legacy selection. No YouTube lease or provider request is made. Applying the reviewed migration permits the same job to resume when next due, subject to current approval and time checks. Creator API admission likewise fails closed with `youtube_capacity_schema` before a provider request. Deploy in the order **review/apply migration → release code → verify migration and worker execution**.

`CapacityController.record()` takes a short PostgreSQL transaction lock for the bound project, checks project/workspace daily budgets and per-workspace rate, commits reservation and attempt meter, then permits the remote API call. The lock never spans network I/O. Unknown/failed provider results consume their reservation; no optimistic refund can permit duplicate cost or exceed the configured ceiling. Pre-request denials are recorded as denied attempts with zero reserved units. Analytics/reporting/resumable requests with undocumented unit cost are metered as unknown units and still subject to per-workspace request limits.

Initial `channels.list` identity discovery uses `record_identity(workspace)` against the exact server-selected OAuth provider's project policy. It reserves one general unit and a request in the same durable project/workspace counters before the callback's workspace lock, because the connection does not exist yet. No fictional channel ID is inserted into the connection-specific attempt log. A consumed callback whose token exchange later fails retains its conservative reservation. Existing-channel discovery and refresh/reverification must also use this trusted admission hook outside workspace locks.

Conservative default **local admission ceilings**, based on Google's current documented defaults, are 100 `videos.insert` calls/day, 100 searches/day and 10,000 general units/day. They are **not a claim about the live Google project's allocation or remaining quota**. Other clients and calls outside this application can consume the same project quota. A provider quota response remains a separate operational hold and requires reconciliation.

An operator can reduce ceilings with `POSTRIFF_YOUTUBE_UPLOAD_DAILY_LIMIT`, `POSTRIFF_YOUTUBE_SEARCH_DAILY_LIMIT`, and `POSTRIFF_YOUTUBE_GENERAL_DAILY_LIMIT`. Raising above default requires fresh `POSTRIFF_YOUTUBE_PROJECT_EVIDENCE` bound to the configured client/project:

```json
{
  "projectId": "ACTUAL_GOOGLE_PROJECT",
  "clientId": "ACTUAL_CONFIGURED_OAUTH_CLIENT",
  "quota": {
    "status": "verified",
    "source": "google_platform",
    "reference": "ACTUAL_QUOTA_DECISION_OR_CONSOLE_EVIDENCE_REFERENCE",
    "observedAt": "ACTUAL_OBSERVATION_TIME",
    "limits": {"videoUploads": 100, "search": 100, "general": 10000}
  }
}
```

This is an evidence schema, not an approval record. Do not fill it with invented approvals. A quota submission, operator assertion, mismatched project/client, or stale proof cannot raise the admission ceiling. Bound clients in one project use the same project key; no project/client rotation is a capacity workaround.

Default workspace ceilings are five upload initiations/day, 20 searches/day, 2,000 general units/day, 120 requests/minute and 20 pending YouTube workflows. Configurable workspace daily limits use `POSTRIFF_YOUTUBE_WORKSPACE_VIDEOUPLOADS_DAILY_LIMIT`, `_SEARCH_DAILY_LIMIT`, and `_GENERAL_DAILY_LIMIT`; they cannot exceed the project ceiling. `POSTRIFF_YOUTUBE_WORKSPACE_REQUESTS_PER_MINUTE` is capped at 600 and `POSTRIFF_YOUTUBE_PENDING_PER_WORKSPACE` at 200. Queue admission belongs in the workspace's existing approval transaction, before creating a new job; idempotent repeats must keep their original receipt.

A known pre-request denial places an upload into `quota_delayed`, retains its exact resumable session, reports the reason/retry time, and resumes the same operation after the Pacific-time daily reset or minute-rate window. It never consumes a fresh `videos.insert` to continue an existing session. DST transitions use `America/Los_Angeles`. Account/client-binding changes hold the existing journal for reconnection; only actual revocation purges authorized data.

The worker now selects tenants with due jobs, oldest durable dispatch first, locks at most 100 candidates, and rotates due jobs within each workspace. Existing lease fencing, membership checks, fresh YouTube identity checks, cancellation, and exact approvals still govern forward execution. Agent-owned jobs additionally recheck finite Autopilot authority at initial claim and immediately before forward execution; paused, revoked or changed policies hold the job. Readback of an accepted native schedule remains allowed, and pausing Autopilot does not cancel a schedule already accepted by YouTube.

`GET` creator overview exposes `quota.admission`: configured project ceilings, workspace ceilings/usage/denials, queue/rate limits, Pacific reset time, whether approved quota evidence was accepted, and `actualGoogleRemaining: null`. It exposes no other workspace's counters. `operationalAlerts` and existing audit events retain quota, restriction and reconnect interventions.

## Throughput evidence and scale boundary

Source inspection found a once-per-minute Vercel cron, shared `tick(max_jobs=10,max_seconds=20)`, and an original 1 MiB chunk. The original idealized ceiling was 10 MiB/minute across all workspaces. With 8 MiB chunks, the corresponding **unmeasured theoretical maximum** is 80 MiB/minute if every lease completes within the time budget; initiation, status requests, identity refresh, processing, attachments, other providers, database contention, and network latency reduce it. This is arithmetic from configuration, not benchmark evidence. Actual provider throughput, end-to-end latency, and 10,000-account load capacity remain **UNVERIFIED**.

The short project quota transaction serializes admission deliberately for correctness. The worker's bounded selection still evaluates due JSON jobs and sorts tenants; it is an incremental fairness fix, not proof of a fleet queue architecture. Before broad rollout, use a remote dedicated queue/worker fleet with indexed relational due jobs, measured capacity, approved concurrency and Google allocations. Avoid duplicate Vercel/queue schedulers that can create unexpected execution load.

Server-only `POSTRIFF_WORKER_MAX_JOBS` and `POSTRIFF_WORKER_MAX_SECONDS` tune a cron invocation while preserving defaults of ten jobs and 20 seconds. Hard ceilings remain 25 jobs and 45 seconds; malformed/out-of-range configuration fails before dispatch with `worker_budget_configuration`. The tick receipt records its chosen budget. These settings do not create more invocations, workers, approved quota or storage capacity. All invocations retain the same short database claim lock, tenant cursor, cancellation/authority checks, lease fences, immutable upload key and project quota reservation. A future fleet must use those shared stores and the actual bound Google project budget. Its scheduler must avoid a synchronized herd: the current nonblocking global claim lock can return no work to competing invocations. Multiple-worker throughput has not been accepted.

The 10,000-customer forecast assumes 3,000 uploads/day averaging 500 MiB. At eight MiB/chunk, each video needs at least 63 chunk leases: **189,000 chunk leases/day**, before initialization, processing, attachments, status reconciliation and other platforms. One default once-per-minute worker has at most 14,400 leases/day, so the arithmetic lower bound is **14 default workers on daily average**. The forecast's 40% two-hour peak needs 75,600 chunk leases in 120 minutes: **63 default workers**. At the maximum 25-job budget the corresponding lower bounds are **six on average and 26 at peak**. Each assumes every permitted chunk completes inside its time budget. They are necessary arithmetic minima, not measured sustainable fleet sizes; additional measured provider/network/DB overhead and operational reserve are required. No fleet or paid compute was provisioned by this patch.
