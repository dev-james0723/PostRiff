# Signed resumable Library video uploads

State: **IMPLEMENTED BUT UNVERIFIED against a real authenticated Storage upload**. Root verified HTTP OPTIONS 200 on staging's actual direct resumable endpoint, with the expected project reference. This establishes endpoint availability only. Production/staging bucket limits, global Supabase limits, the signed protocol and an interrupted real upload require deployment acceptance.

The Library requests `transport: tus` from the existing video-upload-intent endpoint. Legacy chat clients still receive their existing signed PUT ticket. The server signs one new immutable private workspace video object using the existing server-only Storage adapter; the browser receives only the resulting single-object `x-signature`, direct storage hostname, exact bucket/object metadata, limit and expiry. No service key, application bearer, broad role grant, public bucket or upsert is introduced.

The client creates an empty TUS session, validates the returned URL against the exact direct Storage origin/path, confirms the server's file length and byte offset with HEAD, and uploads six-MiB PATCH chunks. Requests omit cookies and reject redirects. After dropped responses, conflict or transient provider errors, HEAD must establish the accepted offset before a chunk may be retried. Recoveries are bounded. A paused/expired/refused upload requires user retry; an expired session never silently creates a new object.

A full-content fingerprint binds the sanitized video, original filename and last-modified time. Hashing reads one six-MiB slice at a time; it does not allocate a whole-video array buffer. Browser session recovery stores only an opaque fingerprint, asset ID, session URL and creation time, scoped by workspace. It never stores a signed token, account/session bearer or service key. Reselecting the original file regenerates and compares its fingerprint before resuming.

On retry, a new authenticated endpoint renews only the original creator's existing pending upload intent, for the same workspace/object/MIME/byte count. It reconciles object HEAD before signing again, so a lost final PATCH response or failed follow-up commit cannot cause a duplicate upload. Current role, plan/bucket limits and pending intent are rechecked; regrant is bounded to 24 hours from original intent creation. Existing committed assets can be recognized without issuing another upload grant. Unknown Storage outcomes are retained for reconciliation rather than overwritten.

The existing server commit remains the final authority: exact object size/MIME/ETag, bounded container reads, duration/dimensions, location-data handling and decoded frames. Successful transport alone never marks a video postable or published. A failed commit can be retried against the same object. Removing a pending upload clears its local recovery reference through the existing authorized abort workflow.

Current [Supabase resumable-upload documentation](https://supabase.com/docs/guides/storage/uploads/resumable-uploads) specifies the signed `x-signature` flow, direct storage hostname, six-MiB chunks and TUS session expiry. [Supabase file limits](https://supabase.com/docs/guides/storage/uploads/file-limits) document distinct global/bucket and protocol ceilings; a product configuration does not enlarge the approved backend limit. The actual configured private bucket and server catalog remain enforced.

Synthetic regressions are in `web/tests/resumable-upload.test.cjs`, `tests/test_hosted_storage_video.py` and `tests/test_video_uploads.py`. They cover chunking, same-file recovery, lost-response reconciliation, expired grants/sessions, redirects, broad-credential refusal, owner/tenant isolation, existing-object reconciliation and refusal to replace uncertain content. Root cloud CI is the validation authority for the complete candidate. No authenticated real Storage upload or large-video provider acceptance is claimed here.
